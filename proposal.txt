1. EXECUTIVE SUMMARY
AI Content Studio is a web‑based platform that automates the generation of large‑scale AI‑created visual and audio content. The primary workflow is:

text
CSV File
   ↓
CSV Validation
   ↓
Scene/Prompt Import
   ↓
Project Creation
   ↓
Batch Generation
   ↓
AI Image / Video Generation
   ↓
AI Voiceover Generation
   ↓
File Storage
   ↓
Progress Tracking
   ↓
Retry / Resume
   ↓
File Selection
   ↓
Export
The system targets users who need to produce hundreds or thousands of AI‑generated assets without manually entering prompts one by one. The user prepares a structured CSV file containing scene information such as Scene ID, visual prompt, voiceover script, filename, aspect ratio, and optional generation settings. Each row becomes an individual generation task.

The application supports user registration and login (via Supabase), multiple projects, CSV upload and validation, bulk generation of images and videos (where supported by Google AI APIs), voiceover generation, secure API‑key management, background jobs, retry and resume logic, progress tracking, file management, selective export (ZIP), and full multi‑user isolation with persistent job state.

3. PROBLEM STATEMENT
Manual AI content generation is time‑consuming and impractical for large projects. A typical manual workflow requires the user to:

Read a script.

Create a prompt.

Open an AI generation tool.

Enter the prompt.

Wait for generation.

Download the result.

Rename the file.

Generate voiceover separately.

Download the audio.

Organize files.

Repeat hundreds of times.

This becomes impractical for large‑scale content production. The proposed system solves this problem by providing a centralised, automated pipeline.

10. COMPLETE SYSTEM WORKFLOW
Registration – User creates an account with email, password, and confirm password. Supabase Auth creates the user.

Login – User logs into the application.

Create Project – User creates a project (e.g., “Ancient Rome Documentary”).

Background Job Creation – A job is created and enqueued.

Worker Processing – Worker processes each scene independently, calling Google APIs.

Progress Tracking – UI updates with real‑time progress (completed/pending/failed).

Retry/Resume – Failed or paused jobs can be retried/resumed without re‑generating completed scenes.

File Management – Generated assets are organised in project folders.

Asset Selection & Export – User selects files and exports them as a ZIP archive.

Persistent State – All data survives logouts, browser closures, and backend restarts.

18. AI GENERATION ENGINE
The generation engine uses a provider abstraction to avoid tight coupling:

text
Generation Provider
        │
        ├── Image Provider
        ├── Video Provider
        └── Voice Provider
Each provider is implemented for Google‑supported APIs. If a provider cannot perform a requested operation (e.g., video generation), it returns an explicit “UNAVAILABLE” state rather than a fake success.

18.1 Image Generation
For each scene with a visual prompt, the worker calls the image generation API, stores the result, and records the asset in the database.

18.2 Video Generation
If the configured Google service/API supports video generation, the worker follows a similar flow. Otherwise, the system displays “VIDEO GENERATION UNAVAILABLE” and does not create fake assets.

19. VOICEOVER GENERATION
For every scene with a voiceover_script, the worker calls a Google‑supported Text‑to‑Speech (TTS) service. The resulting audio file is stored and associated with the scene. Voiceover generation status is tracked independently from visual generation.

20. BATCH PROCESSING & JOB QUEUE
20.1 Generation Job
A generation job aggregates all scenes of a project. It tracks:

text
Total tasks
Completed tasks
Processing tasks
Failed tasks
Pending tasks
20.2 Queue Architecture
Long‑running generation must not depend on an open browser request:

text
Frontend → FastAPI → Job Database → Queue → Worker → Google API
Recommended implementation: Redis + a background task library (Celery, RQ, Arq, or similar) that persists job state.

20.3 Worker Behaviour
Processes one scene at a time (or configurable concurrency).

Generates visual, then voice (order may be configurable).

Updates database status after each step.

Respects configurable concurrency and provider rate limits.

20.4 Concurrency
Configurable (default conservative, e.g., 1‑2 concurrent operations). Should never flood the provider with hundreds of simultaneous requests.

20.5 Quota & Rate Limit Handling
When Google returns 429 (quota/rate limit), the worker pauses the job, sets an appropriate status, and allows the user to resume later. Completed items are preserved.

21. PROGRESS TRACKING
A dashboard displays:

Overall project progress (percentage)

Breakdown by status: completed, processing, failed, pending

Current scene and current operation (e.g., “Generating Voiceover”)

Progress updates happen in near real‑time via database queries (polling or WebSocket, depending on implementation).

22. RETRY & RECOVERY
Retry – Failed tasks are automatically retried up to a configurable maximum attempt count.

Resume – If a job is paused or interrupted (e.g., backend restart), it can be resumed. Already completed scenes must not be re‑generated.

Recovery – Job state is persisted in the database; upon worker startup, pending/in‑progress jobs are reloaded and execution continues from the last successful scene.

26. DATABASE DESIGN
The Supabase PostgreSQL database includes the following core tables (all subject to Row‑Level Security with auth.uid() = user_id):

26.1 projects
id, user_id, name, description, status, created_at, updated_at

26.2 scenes
id, project_id, user_id, external_id, visual_prompt, voiceover_script, filename, aspect_ratio, media_type, voice_name, visual_status, voice_status, video_status, overall_status, created_at, updated_at

26.3 generation_jobs
id, project_id, user_id, status, total_tasks, completed_tasks, processing_tasks, failed_tasks, pending_tasks, started_at, completed_at, created_at, updated_at

26.4 generation_tasks
id, job_id, scene_id, user_id, task_type (visual/voice/video), status, attempt_count, error_message, started_at, completed_at, created_at, updated_at

26.5 api_profiles
id, user_id, profile_name, provider, credential_reference (encrypted), is_active, connection_status, last_tested_at, created_at, updated_at

26.6 assets
id, user_id, project_id, scene_id, asset_type, storage_path, filename, mime_type, size, provider, model, created_at

All tables are protected by Supabase Row‑Level Security policies to ensure a user can only access their own records.

31. MULTI‑USER ARCHITECTURE
Every user exists within their own isolated context:

Supabase Auth provides unique user IDs.

All database tables include user_id and RLS policies.

API routes derive the user identity from the token and scope all queries.

File storage paths are prefixed by user ID or project ID to prevent cross‑access.

32. ERROR HANDLING
Errors are categorised and handled gracefully:

User errors – invalid CSV, missing prompts → clear feedback in UI.

Authentication errors – 401/403 → redirect to login or show permission denied.

Provider errors – quota, rate‑limit, unavailable service → job paused, informative message, not treated as fatal.

Internal errors – 500 → logged with trace ID, generic error shown to user.

33. LOGGING & MONITORING

Application logs structured (JSON) and include correlation IDs for request tracing.

Worker logs capture task attempts, failures, and retries.

Production monitoring should alert on critical failures (queue lag, database down, etc.).
