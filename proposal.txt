1. PROJECT TITLE
AI ContentStudio — Intelligent CSV-Driven AI Image, Voiceover & Video Batch Generation Platform

2. PROJECT OVERVIEW
AI ContentStudio is a web-based AI content production platform designed to automate the generation of large numbers of visual and audio assets from structured or semi-structured CSV files.

The primary purpose of the system is to allow a user to upload a CSV containing content-generation information such as:

Scene information
Image prompts
Video prompts
Voiceover scripts
Tone, Voice, Duration, Aspect ratio, Style
Character information, Camera instructions, Lighting
Master prompts, Negative prompts, Filenames, Media types
Other custom metadata
The system must intelligently understand the uploaded CSV even when the column names or structure are not exactly predefined. The application should automatically:

  ↓

Asset Browser
  ↓

7. TECHNOLOGY STACK
Frontend
The existing frontend should be preserved where practical. It should provide: Dashboard, Projects, Batch Generation, Asset Browser, Selective Export, Settings, Authentication, Live progress interface.

Backend (FastAPI)
FastAPI is responsible for: REST API, Authentication validation, User authorization, CSV processing, CSV analysis, Column mapping, Project management, Scene management, Generation task management, API profile management, Generation orchestration, Error handling, Storage management, Progress APIs, Realtime/event integration.

Database (Supabase)
Supabase is responsible for persistent application data. It should store: Users, Projects, CSV metadata, CSV columns, Normalized scene data, Generation jobs, Generation tasks, Asset metadata, API profiles, Settings, Errors, Statuses, Timestamps, Relationships.

8. AUTHENTICATION
The platform must support:

Registration: User can create an account using Email and Password.
Login: User can log in securely.
Logout: User can log out.
Session persistence: Refreshing the browser must not unnecessarily log the user out.
Protected routes: Dashboard, Projects, Batch Generation, Assets, Settings must require authentication.
9. SETTINGS SYSTEM
The Settings page should allow users to manage their account and AI configuration. The interface should include: Account Information, Security, Google AI Profiles, Generation Defaults, Storage Configuration, Application Preferences.

10. GOOGLE AI API PROFILE MANAGEMENT
The user may have multiple Google AI API profiles (e.g., Profile 1, Profile 2, Profile 3). Each profile contains: Profile Name, Google AI API Key, Status, Usage information if available, Last successful request, Last error, Created date.

11. API KEY SECURITY
API keys must never be exposed to the frontend after being saved. The system should:

Frontend
  ↓
FastAPI
  ↓
Validate API key
  ↓
Encrypt securely
  ↓
Store encrypted value
The frontend should only see: Profile Name, Masked API Key, Status. Example: AI Batch Studio •••••••••••••• Connected ✓

12. API CONNECTION TEST
Every API profile should have a "Test Connection" feature. The test must make a real API request. Possible results: ✓ Connection successful, ✗ Invalid API key, ⚠ Quota exceeded, ⚠ Rate limit reached, ✗ Authentication failed, ✗ Service unavailable. Do not show fake success.

13. MULTIPLE API PROFILE MANAGEMENT
The generation system should support multiple configured API profiles. The worker should select an appropriate available profile. Conceptually:

Generation Task
  ↓
Select API Profile
  ↓
Request
  ↓
Success?
├── YES → Continue
└── NO
      ↓
Quota/Rate Limit?
      ↓
Mark profile temporarily unavailable
      ↓
Select next available profile
      ↓
Retry task
The system must never bypass provider restrictions or violate API terms. It should only rotate among legitimately configured API credentials.

14. CSV UPLOAD SYSTEM
The system must support: Drag and drop, Browse/upload, UTF-8 CSV, Different delimiters when detectable, Reasonable variations in headers, Different column ordering, Optional columns, Custom columns. The user should not be forced to use one rigid CSV schema.

16. INTELLIGENT COLUMN MAPPING
Examples: image_prompt, visual_prompt, visual_description, scene_description may map to: Visual Prompt. Similarly: voiceover, narration, voiceover_script, narration_text may map to: Voiceover Script. The system should use intelligent matching based on: Column name, Data examples, Data type, Content patterns, Existing mappings.

17. CONFIDENCE SCORE
Detected mappings should provide confidence. Example: visual_description → Visual Prompt (98% confidence). If confidence is low: description → ? ⚠ Ambiguous column. The user should be able to manually select the correct meaning.

18. MANUAL COLUMN MAPPING
The user must be able to override automatic mappings. Example:

CSV Column             System Mapping
visual_description  →  Visual Prompt ▼
narration_text       →  Voiceover ▼
tone                 →  Tone ▼
length               →  Duration ▼
Available mappings should include: Visual Prompt, Video Prompt, Voiceover, Tone, Voice, Duration, Aspect Ratio, Filename, Media Type, Master Prompt, Negative Prompt, Style, Character, Camera, Lighting, Language, Custom, Ignore.

19. PRESERVE UNKNOWN COLUMNS
Unknown columns must never be silently deleted. For example: music, emotion, camera_movement, historical_period, custom_style should be stored as custom metadata. The original CSV information should remain recoverable.

20. CSV DETAIL VIEW
After uploading a CSV, the user should be able to open it. Display: File Name, File Size, Upload Date, Rows, Columns, Encoding, Delimiter, Status.

21. CSV COLUMN VIEW
Show: Column Name, Detected Meaning, Data Type, Confidence, Non-empty Count, Example Value.

22. CSV DATA PREVIEW
Display actual CSV rows. Support: Search, Filter, Sort, Pagination, Column visibility, Row inspection. The user should be able to inspect exactly what the system imported.

23. DIFFERENT CONTENT TYPES
The system must support different CSV workflows:

Image only: scene, image_prompt, filename (Generate images)
Voiceover only: scene, voiceover, tone, voice (Generate voiceovers)
Image + Voiceover: scene, visual_prompt, voiceover (Generate both)
Image + Video + Voiceover: scene, image_prompt, video_prompt, voiceover, duration, aspect_ratio (Generate all supported assets)
24. MEDIA TYPE DETECTION
If a CSV contains media_type = image, generate image. If media_type = voice, generate voiceover. If media_type = video, generate video. If no explicit media type exists, infer requirements from available columns.

25. MASTER PROMPT SYSTEM
CSV files may contain master_prompt. The system composes: Master Prompt + Scene Prompt + Relevant Metadata.

26. DYNAMIC PROMPT COMPOSITION
Prompt composition should dynamically use available information. Potential components: Master Prompt, Visual Prompt, Character, Location, Camera, Lighting, Style, Tone, Emotion, Negative Prompt. Only fields that exist should be included.

27. IMAGE GENERATION
For image tasks: Master Prompt + Visual Prompt + Style + Character + Camera + Lighting + Aspect Ratio + Negative Prompt. Generate through the configured Google AI integration.

28. VOICEOVER GENERATION
For voiceover tasks: Voiceover Script + Voice + Tone + Language + Speed + Other applicable settings. Use the configured Google AI/TTS service.

29. VIDEO GENERATION
Where a supported Google video-generation API/model is configured: Video Prompt + Master Prompt + Duration + Aspect Ratio + Style. Generate the video. If a requested operation is unsupported, Unsupported must be shown rather than pretending generation occurred.

30. PROJECT SYSTEM
Users can create multiple projects. Each project contains: Project Name, Description, CSV Files, Scenes, Generation Jobs, Generation Tasks, Assets, Settings, Created Date, Updated Date, Status.

31. SCENE SYSTEM
Each CSV row can become a scene. Example: Scene 001: Image ✓, Voiceover ✓, Video ⏳. Each scene should have its own task state.

32. GENERATION TASK SYSTEM
Each asset generation should become an individual task. Example: Scene 001 ├── Image Task ├── Voiceover Task └── Video Task. Each task has: Task ID, Project ID, Scene ID, Asset Type, Status, API Profile, Prompt, Started At, Completed At, Error, Retry Count, Storage Reference.

33. GENERATION STATUS
Supported statuses: Pending, Queued, Processing, Completed, Failed, Retrying, Cancelled, Skipped, Unsupported.

34. BLUE COMPLETION CHECKMARK
A blue checkmark ✓ must only appear when the asset has genuinely completed. Completion means: AI generation succeeded + output received + output stored/referenced + database updated.

35. LIVE PROGRESS SYSTEM
Display real-time progress. Example: Overall Progress 72%, Images 72/100, Voiceovers 68/100, Videos 35/100. Currently Processing: Scene 73 — Image Generation. Pending: 28. Failed: 2.

36. PROGRESS MUST BE REAL
Never use fake progress. Do not implement setInterval() to artificially increase percentages. Progress must come from: Actual Tasks + Actual Database State + Actual Worker State.

37. REAL-TIME SYNCHRONIZATION

38. BROWSER REFRESH RECOVERY
If 73/100 were completed before refreshing, after refreshing the page it should still show 73/100. The state must come from persistent backend/database data.

39. FAILURE MANAGEMENT
If a task fails: Scene 34 Image ❌ Failed. Display an appropriate error. Provide: Retry. Retry should create/requeue a real task.

40. BACKGROUND PROCESSING
Long-running generation must not depend on an open browser request. Use a background worker/task queue architecture.

User clicks Start
  ↓
FastAPI creates generation job
  ↓
Tasks enter queue
  ↓
Worker processes tasks
  ↓
Database updates
  ↓
Frontend monitors status

Google API

42. ASSET BROWSER
The Asset Browser should show generated assets. Support: Images, Audio, Videos. Filters: Project, Scene, Asset Type, Status, Date, Filename. Each asset should display: Preview, Filename, Type, Scene, Status, Created Date.

43. SELECTIVE EXPORT
The application must allow users to select: Individual files, Multiple files, Individual scenes, Multiple scenes, Folders/categories, Entire projects. Then export selected assets.

44. FOLDER-BASED ORGANIZATION
Generated assets should be organized logically. Example:

Project/
├── images/
├── voiceovers/
├── videos/
└── metadata/

46. USER DATA ISOLATION
Every user's data must be isolated. User A must never be able to access User B's projects, CSV files, API keys, generation tasks, assets, metadata. Use Supabase Row Level Security and backend authorization appropriately.

47. API PROFILE DATA
Store API profile metadata securely. Never return raw API keys to the browser after storage.

48. ERROR HANDLING
Every API request should have: Loading, Success, Error, Timeout, Finally. No UI should become permanently stuck on Saving... Loading... Generating... Processing...

49. NETWORK FAILURE HANDLING
If the backend becomes unavailable: "Backend unavailable" should be shown clearly. The frontend should not silently wait forever.

50. API TIMEOUTS
Every external API request should have reasonable timeout handling.

Task
  ↓
Timeout
  ↓
Retry policy
  ↓
Retry or Failed
51. RETRY SYSTEM
Retry should support: Failed API calls, Temporary network failures, Rate limits, Temporary provider failures. Do not endlessly retry permanent failures.

52. SECURITY
The system must: Protect API keys, Protect user sessions, Validate file uploads, Validate API requests, Prevent unauthorized project access, Use secure database policies, Avoid exposing secrets in logs, Avoid exposing secrets in frontend JavaScript.

53. DYNAMIC UI REQUIREMENT
Nothing important should be hardcoded. Do not hardcode: Project count, Scene count, Progress, Completed count, API profiles, CSV filename, Rows, Statuses, Generated files, User information. All values must come from actual backend/database state.

54. DASHBOARD
Dashboard should dynamically show: Total Projects, Active Jobs, Completed Assets, Processing Assets, Failed Assets, Images Generated, Voiceovers Generated, Videos Generated. Recent projects and jobs should also come from the database.

55. PROJECT STATUS
All values must be calculated dynamically based on actual database records.

56. NO MOCK DATA
The production application must not rely on: Fake API responses, Fake progress, Fake completed assets, Hardcoded statistics, Mock database records, Placeholder success messages.

57. LOGGING
The backend should log useful operational information. Never log raw API keys.

58. AUDITABILITY
Every generation task should be traceable. The system should be able to answer: Which project? Which scene? Which asset? Which prompt? Which API profile? When started? When completed? Did it fail? Why did it fail? Was it retried? Where is the output?

59. SCALABILITY
The system should be designed so that 10 scenes and 1,000 scenes use the same architecture. Generation must be task-based and asynchronous.
